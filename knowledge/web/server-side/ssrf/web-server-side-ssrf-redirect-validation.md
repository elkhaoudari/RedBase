# SSRF via Redirect Validation Failure

## Summary

A URL submitted by the requester passes validation because its initial
destination is permitted. That destination returns a redirect to a second
location that was never validated. If the fetch client follows redirects without
re-applying the same policy to each hop, the second request reaches the
unvalidated destination.

## Root cause

Validation is applied to a request, not to a chain. The policy that governs the
first request is not re-evaluated for each subsequent request generated by the
client's redirect handling. This is a distinct mechanism from URL parser
confusion: the validator and the client agree on what the initial URL means. The
failure is that there is no policy enforcement beyond the first hop.

## How it works

1. The application validates the supplied URL against an allowlist.
2. The URL passes because its host is permitted.
3. The application issues a request to the permitted host.
4. The permitted host responds with a `3xx` status and a `Location` header
   pointing at an internal destination.
5. The HTTP client follows the redirect, connecting to the internal destination
   without re-consulting the policy.
6. The internal destination is reached from the server's network position.

The vulnerability depends on two properties of the fetch client:

- Whether it follows redirects at all. A client that refuses redirects is not
  exploitable through this mechanism.
- Whether it re-validates each hop against the same policy. A client that does
  re-validate is not exploitable through this mechanism.

## Common contexts

Any application that fetches a user-supplied URL with redirect following
enabled — webhook configuration and testing, URL import, link preview,
screenshot rendering, OAuth/OIDC discovery, JWKS URL validation.

## Variants

- **Simple redirect** — one `3xx` from a permitted host to an internal
  destination.
- **Chained redirect** — permitted host redirects to a second permitted host
  which redirects to an internal destination. A policy that re-validates the
  first hop but not subsequent hops is defeated by the chain.
- **Protocol-relative redirect target** — the `Location` header contains
  a reference such as `//<ip>/path`. The client resolves it against the
  current URI. The resulting absolute destination must still be validated
  before the next request.

## Detection and testing considerations

Requires a host under tester control that issues a `3xx` in response to the
submitted URL. The tester needs to observe the second request — through a
callback on the second hop, through a response difference, through timing, or
through a side effect on the internal destination.

Confirmation depends on the client's redirect behaviour. Test with a permitted
host that redirects to another permitted host (which should succeed and prove
the client follows redirects) and with a permitted host that redirects to an
internal destination (which is the actual test).

A client with redirect following disabled will not reach the second hop, and
this technique does not apply. A client that follows redirects but applies the
policy per hop will not reach the internal destination. Neither absence is
evidence that the first request was not made; only that this specific mechanism
is not exploitable against that specific client.

## Mitigations

- Disable redirect following where the feature does not require it.
- Where redirects must be followed, re-validate the destination on every hop
  against the same policy applied to the original URL.
- Resolve and validate before each hop rather than at the start of the chain.
- Enforce the same policy in the egress proxy, so a client that follows
  redirects without re-validating still cannot reach a forbidden destination.
